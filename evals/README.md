# Evals

A small, honest eval of the tutor, through the same `POST /api/tutor` endpoint and request schema the app uses. The harness runs in Node and judges chords with `src/theory`, so no theory is duplicated. Latest results: [results/README.md](results/README.md).

**What it measures, and why.** Ear training is improvisational: you try a chord, the tutor explains the theory and says "maybe, but why not try these?", and those ideas have to be playable right away. So the headline is not whether the tutor names the chord a 1920s hymnal printed, but whether it offers **playable, plausible alternatives**: at least two distinct chords, as cards the student can audition, judged plausible by code where they are placed, with no reference answer needed. An off-target idea beside them (a deliberate contrast, say) doesn't take that away; the share of off-target ideas is reported on its own line. Around it, code reads the message itself: no verdict words, every bar it cites exists, a repeat in the melody pointed out at both places, at most three numbered tests, and every chord it names as an alternative backed by a card. "Includes the conventional choice" survives as a secondary line.

The tutor has two modes (`mode` in the request): **review** analyzes the whole chart, with no question needed; **question** answers the student's question about it. The eval asks both: a review of each of four public-domain hymn tunes ([dataset](dataset/README.md)) with the hymnal's printed chords placed as the student's chart; a review of each of the app's four demo tunes (`content/songs`: St. James Infirmary, Sweet Georgia Brown, When the Saints Go Marching In, Greensleeves) with the dropdown's top pick placed at every downbeat; and "does this work?" questions about a chord placed at a few downbeats of each demo tune.

## Running it

```sh
make dev                       # or any running server
node evals/run.js              # default http://127.0.0.1:8000
node evals/run.js --url http://127.0.0.1:8001
node evals/run.js --limit 3    # smoke run: first 3 requests, prints a summary, writes nothing
node evals/run.js --concurrency 1   # one request at a time (default 4)
node evals/score.js            # re-score results/latest.json, no requests (make eval-score)
```

Scoring is separate from asking: `run.js` records each reply, with the suggestions the server sent, and hands them to `score.js`, which scores them and writes the results. Run on its own, `score.js` re-scores a saved `latest.json` with zero requests, so a change to the scoring never needs the tutor asked again.

- `--concurrency N` keeps up to N requests in flight; the default, 4, matches the server's `TUTOR_MAX_CONCURRENT`. The first request goes alone, so a wrong access code costs one strike, not one per worker; the pool starts after it. The server frees a slot only when a stream ends, so a pool as wide as the cap can still be answered `503 busy`; the harness waits out its `Retry-After` and retries, as for a rate limit. Replies finish in any order, but `latest.json` keeps them in request order, so a run's results don't depend on the concurrency (only the latencies do). `--limit` still sends the first N requests in that order.

- `EVAL_URL` replaces `--url`.
- `TUTOR_ACCESS_CODE`, when set, is sent as `X-Tutor-Access` (the live tutor's passphrase), percent-encoded as the app sends it. Fixture mode needs none. If the live tutor answers `401 access_required` (code missing or wrong) or `429 access_locked` (too many wrong codes), the harness says so and stops at once, without retrying: the whole run ends, including requests still in flight.
- Any other thrown error (the server going away mid-run, say) also ends the run, and no results are written. HTTP and stream errors the tutor reports are recorded as failed replies instead.
- The model reported in the results is the `served_by` of the replies the server's own model served, so the harness needs no setting for it.

### A live run

```sh
export ANTHROPIC_API_KEY=… TUTOR_ACCESS_CODE=…   # in your shell; never in a file
make eval-live                                   # 3-request smoke run, then asks
make eval-live CONFIRM=1                         # the same, without the question
```

`make eval-live` (`scripts/eval-live.sh`) starts a local server on a free port with `TUTOR_MODE=live`, `TUTOR_RATE_LIMIT="240/minute;4000/day"` (four requests in flight can pass 60 a minute, so the limit leaves room for the default concurrency), and `TUTOR_DAILY_TOKEN_BUDGET=2000000`, taking the key and the access code from the caller's environment only (it fails fast if either is unset, never prints them, and never reads `.env`). It waits for `/api/health` to report live mode, sends `--limit 3`, and prints how to check that smoke run's cost in the Anthropic Console before asking whether to send the full run (20 requests). With no terminal to ask, it stops unless `CONFIRM=1` is set. The server stops when the target exits.

One run is 20 requests: 8 reviews (4 hymns, 4 demo tunes) plus 4 demo tunes × 3 "does this work?" questions (12), down from 151 when every hymn change point was asked at three hint levels. A review covers the whole chart in one reply, so fewer requests see more of each song. The server's default limit is 10 a minute and 100 a day per IP, so run against a local server with `TUTOR_RATE_LIMIT` raised. The harness waits out a `rate_limited` 429's or a `busy` 503's `Retry-After` (at most 120 s; 60 s if the header is missing or not a number of seconds) and retries, up to three times. Try a live server with `--limit` first.

The harness asks `/api/health` which mode the server is in. In fixture mode the server replays its canned replies (about Ode to Joy, not these tunes), so a fixture run measures the plumbing, not the model, and the results say so.

## What each request is

A **review** (`mode: "review"`, no question, no history): the song with the student's chart. For a hymn tune, the chart is the hymnal's printed chords; for a demo tune, the dropdown's top pick (`baselineChord` on the bare melody) at every downbeat after the pickup (`dataset/demos.js`, `demoChart`), as a student who took the first suggestion each bar would have it. The snapshot comes from the app's own `toTutorSnapshot`, in Roman-numeral style, built in `request.js`.

A **check** (`mode: "question"`, "does this work?"): the melody with one plausible chord placed on a downbeat (the dropdown's second pick there, or its first when the second isn't plausible) and the question "Does _numeral_ work under the melody note at bar _b_, beat _n_?". Three downbeats per demo tune, spread evenly through them. A good reply explains, then offers other things to try; it doesn't pass a verdict.

The request never carries the song's title (`request.js` strips any, tested in `tests/evals/request.test.js`), so the model can't look up a famous hymnal harmonization by name. A caveat remains: these are well-known tunes, so some recall from the melody alone is possible, and a hymn review shows the hymnal's chords anyway.

**Limits of reading prose by rule.** The chord reader skips a bare "I" or "i" (the pronoun), a bare letter (a melody note: "the long E"), a bare digit (a degree or a bar), and "in G major" (the key), so "go back to I" or "try F" goes unread. A chord named only to explain ("the E is the third of C") reads as an alternative and needs a card; so does a chord given to the student in words the patterns miss ("what you've got in bar 3 is IV"). Bar citations cover the whole sentence they sit in. Numbered tests written inline as "1." aren't counted. Each errs toward passing ordinary prose; a failure is worth reading in `latest.json` before believing.

### Plausible, by code

`plausible` in `metrics.js` judges one suggestion at one melody note, with no reference answer, reusing `src/theory`:

1. **Well-formed:** its numeral and letter name the same chord in the key.
2. **No clash:** the melody note is a chord tone or a tension over it, by `analyzeNoteOverChord`.
3. **Fits:** `fit` on the bare melody, from the note to the end of its bar, is at least **0.5** (`FIT_THRESHOLD`).
4. **Recognized:** a diatonic chord (minor also takes its raised V and vii°), a chord the dropdown's extended list offers (secondary dominants, borrowed chords, passing diminished sevenths), or any applied dominant or leading-tone chord the numeral names (V/x, V7/x, vii°/x). A seventh or sixth counts as its triad.

**Why 0.5.** At the hymns' 41 change points, the chords the hymnals printed score, on the bare melody: one at 0.40, then 0.57, 0.70, and the rest 0.73 to 1.00 (20 of them 1.00). 0.40 is what a lone melody note scores when it is only a tension over the chord and nothing else in its span is a chord tone, so the gap from 0.40 to 0.57 is where "the melody is mostly a chord tone" begins. 0.5 sits in that gap: it passes 40 of the 41 printed chords (the miss is a B, the V, in God Rest Ye, over a melody note that is only a tension), and it rejects a chord whose only contact with the melody is a tension. The dropdown's own top 3 at those points ranges from 0.40 to 1.00, so the threshold also separates its weakest fallbacks from its real fits.

The threshold stays at 0.5, set before any live run. The results also report the headline (and the dropdown's) at 0.4 and 0.6, as a sensitivity line, never to pick a value.

Key-identification accuracy (PRD section 7) isn't measured yet: every request carries the confirmed key.

## Files

- `run.js`: the harness. `jobs.js`: every request and baseline note, shared by `run.js` and `score.js`. `score.js`: scoring a run's replies, and re-scoring a saved one. `request.js`: the request body. `tutorCall.js`: one timed exchange. `metrics.js` (chords and plausibility), `prose.js` (reading the message), `summary.js`: pure scoring, tested in `tests/evals/`.
- `dataset/`: tunes, sources, and `derive.js`.
- `results/latest.json`: the last run, with every reply. `results/README.md`: its table.
