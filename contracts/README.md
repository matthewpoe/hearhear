# Contracts

Phase 0 froze these interfaces so the Phase 1 streams can build in parallel. **A stream changes a contract only by asking Matthew**, and the change and its reason are logged in `docs/decisions/<stream>.md`.

## Data contracts (JSON)

| File                        | What                                                                                      | Source of truth                                                   | Consumers                         |
| --------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------- | --------------------------------- |
| `song.schema.json`          | The song model: absolute pitches in ticks (12 per quarter), plus key and meter hypotheses | This file                                                         | store, content validation, evals  |
| `tutor-request.schema.json` | `POST /api/tutor` body: a readable snapshot with no MIDI, the question, and history       | **Generated** from `server/hearhear/models.py` (`make contracts`) | tutor panel, evals                |
| `tutor-reply.schema.json`   | The tutor's reply, sent as the structured-output schema (`output_config.format`)          | **Generated** from `server/hearhear/models.py`                    | proxy, tutor panel, evals         |
| `tutor-sse.md`              | The streaming protocol and error codes                                                    | This file                                                         | proxy, tutor panel, evals         |
| `functions.json`            | Harmonic function per numeral and mode, with its color token and shape                    | This file                                                         | `functionOf` and `functionInfo`   |
| `fixtures/tutor/*.json`     | SSE shape fixtures for fixture mode and tests                                             | This directory                                                    | proxy (fixture mode), tutor panel |

Wire format is snake_case (Python side); the in-browser song model is camelCase. `toTutorSnapshot` is the only place that crosses between the two.

## Shared surfaces: who writes, who reads

- **Tutor suggestions:** Stream F validates each reply client-side and writes `suggestions`. Stream D2 reads it and offers each suggestion as an alternative to audition. Nothing applies a suggestion to the song except the user choosing it in D2's dropdown.
- **Chord chip row** (shape, color, and numeral or Nashville label for each chord): Stream D2 owns it. The staff (Stream C) shows chord letter names colored by function, as a lead sheet does, with no shapes and no second chip row (decision D3). In hidden mode a chord shows as a neutral mark with no name (D2).
- **Audition:** D2 calls `auditionChord(voicing, range, { atTick, neighbors })` with `neighbors` from `ui.auditionVoicing`. With "as-song" (the default), Stream B plays the melody and every other placed chord exactly as in the song, so A/B comparisons differ only in the candidate's harmony; with "from-candidate", the following chord voice-leads from the candidate (decision D4). After a commit, the phrase replays with natural voice leading. Closing the dropdown calls `stopAudition()`, never `stop()`; it also cancels a pending debounced audition.
- **Key labels have three modes** (`keyLabelMode(song, ui)` in `src/store/ui.js`), and Streams C, D1, and D2 all read them:
  - **hidden:** a demo before the guess. No degrees, numerals, Nashville numbers, or function colors, and C renders the staff with no key signature, writing accidentals on the notes.
  - **tentative:** free play on the provisional C. Labels and colors show in the tentative style (tokens in `tokens.css`).
  - **confirmed:** everything derives from the committed hypothesis, even a wrong one.

  The change to confirmed is a reveal: the staff and keyboard fill with color.

- **Starting a demo (Stream D3):** load the tune with `key: { tonic: "C", mode: "major", provisional: true }` and set `ui.demoAwaitingGuess`. The number row plays the provisional C, just as in free play. The tune's true key stays in its content file and the guided-path script, for the drone test and for hints. Committing a guess calls `song.rekey(guess)` with `provisional: false`, which remaps the number row and reveals the labels. After a wrong guess, the guided path points to the drone test rather than correcting the user.
- **Voicing.** Every chord in a passage is voiced with `voice(chord, previous, { below })`, where `below` comes from theory's `passageBelow(song, range)`: the lowest melody note that starts inside the range. B, D2, and D3 all use that one helper. Voicings never go below C2 (decision D9).
- **Keyboard lighting:** `ui.keyboardLights` carries the keys to light, with a `source` of `"playback"`, `"hover"`, or `null`. The chord dropdown (D2) writes it on hover and focus, but only while `source` isn't `"playback"`. `playWithVisuals` writes it during playback, including the key-finding tests. Each writer clears the lights only while `source` is still its own. The piano (D1) renders confirmed chord tones as a fill in `--fn-*` with marks in `--fn-*-ink`; tentative ones as an outline and mark in `--fn-*-on-white-key` or `--fn-*-on-black-key` at full opacity; melody in a neutral highlight, and checks `keyLabelMode` itself, showing no function color when it is hidden.
- **Selection and the chord row (Stream R):** the chord dropdown owns `ui.selectedNoteId`, setting it to the note it opens on and clearing it on close; the chord row (A–J) assigns to that note. A held chord-row chord lights through `heldChord` in `src/input/NumberRow.js`, a separate channel from `ui.keyboardLights`, shown only when no writer owns the lights.
- **Transport and playback:** Stream C owns `src/staff/Transport.svelte` (Play and Stop beside the staff) and `src/staff/playback.js`. `playWithVisuals` is the only way to play the song with visuals. It owns `ui.playheadNoteId`, the staff's playing highlight, and keyboard lights while it plays. D3's key-finding tests call it with `{ chords: [], drone }` rather than calling `playPhrase` themselves (decision D10). `drone()` and `playWithVisuals`' `drone` option take a MIDI number, an array of them (a chord), or null.
- **Theory additions from Stream A's round-1 fixes (merged):**
  - `passageBelow(song, range) → number`: MIDI of the lowest melody note that starts inside the half-open range, 60 if none.
  - `functionInfo(fn) → { shape, color, meaning }`: shape is `"circle" | "triangle" | "square" | "chip"`, color the CSS custom-property name, from `functions.json`. Unknown input reads as `other`.
  - `transposeSong(song, semitones, { prefer })`: the optional `prefer` is `"sharps"` or `"flats"`. By default it picks the key signature with fewer accidentals, and on an exact tie F# major or Eb minor.
  - `guessRhythm(events)` returns `{ notes, beatMs, dropped }`. `dropped` lists event indexes merged as slips, so callers can pair events with notes.
  - **`candidates()` is ordered most common first.** Callers sort by fit with a stable sort and never reorder first, so fit ties go to the commoner chord.
- **Silent audio start (fix round 2):** `resume() → Promise<void>` in `src/audio/index.js` starts audio from a user gesture without the sound-check chord, and resolves whether or not it started. The chord dropdown calls it when it opens on a note, so its first hover auditions; the landing's first-click warm-up calls it instead of `unlock()` once a tune is loaded. Either way a C chord never sounds over a tune in another key. Nothing outside `src/audio/` imports Tone.
- **Function shapes and colors:** colors and shapes come from theory: `functionOf` for the function, `functionInfo` for its shape, color token, and meaning. Nothing else reads `contracts/functions.json`. Every view draws shapes with `src/lib/FunctionMark.svelte`.
- **Beginner explainers:** `content/explainers.json` is Matthew's copy. Views render it and never rewrite it.
