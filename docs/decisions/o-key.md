A musician friend didn't follow "Is 1 really home?", and Matthew set the new wording. **Deviates from the PRD's voice line** ("Is 1 really home? What key do you think this is?"). _Rejected:_ keeping the PRD wording with a gloss under it.
- **2026-10-07 — "Hear the tune" is gone from the key question.** The staff header already has Play. _Rejected:_ keeping it for the drone-less listen (two Play buttons a few pixels apart).
- **2026-10-07 — One click commits a key; clicking the chosen chip again takes it back.** Matthew: two clicks to pick a key was confusing. A home chip calls `song.rekey({ tonic, mode, provisional: false })`, the same commit "Make … home" made, so the reveal (keyLabelMode turns confirmed) is unchanged. Clicking the chosen chip re-keys to the key as it was before any guess (the provisional C in a demo), and `demoAwaitingGuess` is still set (D18 never clears it on a guess), so the labels hide again. Every change is one undoable rekey. The chips are buttons with `aria-pressed`, and a polite status line says "Home is D major." or "No home chosen yet." The transitions are pure functions in `src/finding/keyChoice.js`, with tests. _Rejected:_ radio chips plus a commit button (the two-click flow); a separate "Clear" button (Matthew asked for click and un-click).
- **2026-10-07 — Bright (major) / Dark (minor) re-commits the chosen home in the new mode** (D major to D minor, Db major to C# minor, respelled for that mode's chips). Before a guess it only sets which mode the next chip commits. _Rejected:_ the mode switch taking the guess back (it'd lose the home the user picked).
- **2026-10-07 — The key question stays open after a guess, with the result under the picker.** Un-clicking only works if the chips are still there. GuessResult is now three short lines inside the prompt: "Home is D major.", the next step (Matthew's wording), and "Not sure? Check it by ear", which opens the finder. It no longer takes focus (focus stays on the chip the user clicked; the status line announces). "Not now" appears once the key is committed, and "Change the key" reopens it. _Rejected:_ swapping the prompt for the result (the old flow; no way to un-click).
- **2026-10-07 — The ear finder holds the tonic chord, not a single note.** The drone test didn't work as a thin single tone, and Matthew wants the full chord. It's the root-position triad of the candidate's mode, in the highest octave whose top note is below the melody's lowest note, with the root never below C2 (D9). The audio engine's drone is a `Tone.PolySynth` of triangle voices with a 0.6 s attack and 1.5 s release at −22 dB per voice, so three voices sit under the piano. _Rejected:_ a piano-sampled chord (decays, so it can't be held under a whole tune); voicing it through theory's `voice()` (a held drone is a fixed triad, not a voice-led progression).
- **2026-10-07 — `drone()` takes a chord: `drone(tones: number | number[] | null)`.** A single MIDI number still works, so `playWithVisuals` (Stream C) is unchanged. **Extends the audio contract's signature** (backward compatible), as the brief asked; recorded as a contract request so `contracts/README.md` can say so.
- **2026-10-07 — The finder passes only the root to `playWithVisuals` and swaps in the full chord at once.** The driver's `drone` option is typed as one note, and it holds, lights, and releases the drone. `listen()` calls the driver with the root (so the keyboard lights the root and the driver's cleanup releases the drone), then calls `drone(chord)` before any sound starts. Each `drone()` call replaces the last, and a pending attack checks that it is still current, so the root never sounds alone. Known gap: the keyboard lights the root only, not all three tones; a contract request asks Stream C to accept an array. _Rejected:_ editing `src/staff/playback.js` (Stream C's file); calling `playPhrase` directly (breaks D10, no playhead).
- **2026-10-07 — The finder offers rankKeys' top three, shuffled per song, with no current-home slot.** The old finder always put the current home (the provisional C) first, which made C a candidate on every tune. Now the provisional C appears only if the ranking puts it in the top three (tested on a C-major scale). The set is shuffled by a seeded Fisher-Yates (FNV-1a hash into mulberry32): the first set by the song id, later sets by id and set number, so the order is stable per tune but the likeliest key isn't always chord 1. On both demos the true key ranks first and lands in another slot (chord 2 for Ode to Joy, chord 3 for St. James), and a test pins that. "None of these sound like home? Try three more" moves to ranks 4–6, and so on, wrapping after 24 keys; chord numbers run on (4, 5, 6). rankKeys is untouched. **Revises D3's wave-1 log entry** ("rank order, no shuffle") at Matthew's request. _Rejected:_ `Math.random` (order changes on every open, so "chord 2" means nothing the next time); rank order (the answer is always first).
- **2026-10-07 — Choosing a chord in the finder is the same action as clicking its chip,** including un-choosing it, and the chosen row names the key ("Chord 2: D major"). Names stay hidden until then.
- **2026-10-07 — The finder closes with a visible Close button or with Escape while focus is inside it,** and focus goes back to "Help me find it", which stays available before and after a guess (with `aria-expanded`).
