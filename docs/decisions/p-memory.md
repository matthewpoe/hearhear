# Stream P: songs and the passphrase remember themselves

Format: **date — decision.** Why. _Rejected:_ alternatives.

- **2026-10-07 — Each song is saved in sessionStorage under `hearhear.song.<id>`, and the open song's id under `hearhear.openSong`.** Matthew: "The songs should be stateful when you load the page... Use session storage." The entry is `{ schemaVersion, song, demoAwaitingGuess }`: the song as the user has it (key with its provisional flag, notes, chords, meter, tempo, title) plus the demo flag that decides hidden labels. This tab only; nothing goes to localStorage. _Rejected:_ localStorage (outlives the tab, which Matthew didn't ask for); one entry holding every song (one corrupt write would lose them all).
- **2026-10-07 — Saves are debounced 300 ms after the last song change or demo-flag change, and switching songs saves the song being left at once.** The pending save holds the song as it was when it changed, so a switch inside the 300 ms window saves the old song under its own id, never the new one. The page also flushes on `pagehide`, so a reload right after an edit keeps it. Other UI state (hover, selection, playhead) doesn't trigger saves. _Rejected:_ saving on every change (writes JSON on every note during noodling); reading the current song when the timer fires (would save the new song and drop the old one's last edit on a fast switch).
- **2026-10-07 — The stored shape is versioned (`schemaVersion: 1`, separate from the song's own `schemaVersion`), and anything that doesn't match is ignored and overwritten by the next save.** A saved copy must parse, carry the current version and a boolean demo flag, match the tune's id, pass a plain-JS version of `song.schema.json`'s checks, and pass `validateSong`. The browser bundle has no JSON Schema validator (Ajv is a dev dependency only), so `persist.js` mirrors the schema's field checks by hand; the content validator and tests keep using the real schema. _Rejected:_ shipping Ajv to the browser (new runtime dependency); trusting stored JSON after `validateSong` alone (it doesn't check types or ranges).
- **2026-10-07 — `song.open(tune)` is the chooser's action: a valid saved copy of `tune.id` loads, with its demo flag; otherwise the tune starts fresh exactly as `loadDemo` does.** `loadDemo` lives in `src/finding/demoTunes.js`, which this stream doesn't own, so `open()` reaches it through hooks: `song.setOpenHooks({ recall, fresh })`, installed once by `installPersistence` in `main.js`, with `fresh: loadDemo`. Until hooks are installed (tests, evals), `open()` is `load()`. Restoring a saved copy gets the same view reset as a fresh demo (audio stopped; selection, playhead, and keyboard lights cleared) with the saved demo flag. _Rejected:_ importing the UI store and audio into `song.js` (the song store stays free of UI and audio, so evals and node tests can use it); copying `loadDemo`'s body into the store (two setups to keep in sync).
- **2026-10-07 — Undo history is per page and starts empty on `open()`, as with `load()`.** Only the song is remembered, not its undo stack, so switching back to a song or reloading can't undo past that point. _Rejected:_ storing the undo stack (up to 200 songs per entry, and the brief scopes it out).
- **2026-10-07 — On page load, `main.js` reopens the song that was open in this tab, before the first render, and only then starts watching for changes.** Reopening goes through `song.open`, so it gets the same validation and demo-flag restore as the chooser. Watching starts after, so the empty starting song never overwrites a saved one. If nothing valid is saved, the page starts as before. The initial "untitled" free-play song is remembered like any other.
- **2026-10-07 — Storage failures never break the app.** Every storage call (including reading `window.sessionStorage` itself, which throws when site data is blocked) is wrapped; the first failure logs one `console.warn`, and after that the app runs as if nothing were saved. Corrupt JSON reads as "nothing saved" without a warning, since the next save repairs it.
- **2026-10-07 — Deviation from DECISIONS.md ("The live tutor requires a passphrase": a typed code is kept in memory only): a typed passphrase is now kept in sessionStorage for this tab, under the same key as a `#code=` link's code.** Matthew overruled the memory-only rule: "the passphrase should be retained if you reload the page. Use session storage." A code the server rejects (`access_required`) or locks out (`access_locked`) is still forgotten, in memory and in storage, so a reload doesn't resend it. Never localStorage. DECISIONS.md line "The browser keeps it in memory for the page session only" needs Matthew's update; this stream can't edit it.
- **2026-10-07 — Nothing tutor-related is stored besides the passphrase:** no conversation, no suggestions, no hint level. Suggestions are tied to a song version, which `load` replaces anyway.
